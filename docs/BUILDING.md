# Building and flashing

## Toolchain

- ESP-IDF **v6.0.1**. Install it with the ESP-IDF tools installer, or clone the tag and
  run its `install.sh`. Other versions are untested.
- The Python environment that the ESP-IDF install script creates.
- For the host tools, in a virtual environment: `pyserial` (`tools/bootlog.py`), `fido2`
  2.x (`tools/hidctl.py`, `tools/fido_test.py`), `cryptography` (`tools/fido_test.py`),
  and `websockets` (`tools/ws_check.py`). No versions are pinned in this repository.
- A C compiler (`cc`) for the host tests.
- `gzip`, which the build uses to compress `web/`.

## Build configurations

There are three. Each is a set of Kconfig defaults files applied in order, and each
builds into its own directory.

| Configuration | Defaults files | Build directory | Use |
|---|---|---|---|
| Release | `sdkconfig.defaults` | `build_rel` | The firmware to ship. The only one to flash on a board that holds credentials |
| Development | `sdkconfig.defaults;sdkconfig.dev` | `build_dev` | Enables `CONFIG_DEV_BACKDOOR` (`sdkconfig.dev`) |
| Test | `sdkconfig.defaults;sdkconfig.dev;sdkconfig.test` | `build_test` | Used by `tools/fido_test.py`. Includes the development options, and also grants user presence without a press and keeps eFuses in RAM |

The configuration commands from the repository root, after sourcing ESP-IDF:

```sh
. "$IDF_PATH/export.sh"

# Release
idf.py -B build_rel -D SDKCONFIG=build_rel/sdkconfig -D SDKCONFIG_DEFAULTS="sdkconfig.defaults" build

# Development
idf.py -B build_dev -D SDKCONFIG=build_dev/sdkconfig -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.dev" build

# Test
idf.py -B build_test -D SDKCONFIG=build_test/sdkconfig -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.dev;sdkconfig.test" build
```

These commands are written from the defaults files and the build scripts. They have not
been run as part of preparing this repository.

`sdkconfig` in the repository root is a generated file and is not committed. The
committed defaults are `sdkconfig.defaults`, `sdkconfig.dev`, `sdkconfig.test`, and
`partitions.csv`.

### What the release configuration sets

- 16 MB flash, QIO at 80 MHz, and the custom partition table in `partitions.csv`.
- 8 MB octal PSRAM, usable by `malloc`.
- Console on UART0, because TinyUSB owns the USB-Serial/JTAG peripheral.
- Wi-Fi CSI on. NimBLE in observer role only.
- TinyUSB with CDC-NCM and two HID interfaces.
- Core dumps to flash.
- `CONFIG_DEV_AUTORECOVER=n`. It must stay off for any build that ships.
- No flash encryption and no secure boot.

### Development options

These are declared in `main/Kconfig.projbuild`:

- `CONFIG_DEV_BACKDOOR` (line 15) is declared under the "Development" menu, default `n`.
  It enables the vendor CTAPHID commands `0x51` and `0x52`, the `/api/log` route, and
  immediate download mode on `POST /api/reboot?mode=download`. `sdkconfig.dev` sets it.
- `CONFIG_DEV_AUTORECOVER` (line 27) depends on `CONFIG_DEV_BACKDOOR`. With it on, the
  board enters ROM download mode if no HTTP request is served within 60 s of boot.
- `CONFIG_FIDO_TEST_AUTO_UP` is under the "FIDO authenticator" menu, default `n`. It
  makes every FIDO touch succeed without a press.

Do not flash a development or test build onto a device that holds credentials you need.

### NCM patch

The build applies `patches/tinyusb-ncm-ndp-bound.patch` to the managed TinyUSB component
automatically. The top-level `CMakeLists.txt` runs at every configure:

- If the patched line is already present, it does nothing.
- If it is absent, it applies the patch with `patch -p1 --forward`.
- If the patch does not apply, configure stops with an error.

The patch is checked against espressif/tinyusb 0.19.0~3. If the component manager
fetches a different version, the configure step fails and the patch must be reviewed.
The manual command is in the header of the patch file, for use if the automatic step is
bypassed.

`managed_components/` is regenerated by the component manager. The patch is applied again
on each configure, so no manual step is needed after a fetch.

### Web assets

`main/CMakeLists.txt` gzips every file under `web/` at configure time and embeds it in
the firmware. A change to an existing file under `web/` is picked up by the next build.
A new file under `web/` needs a reconfigure (`idf.py reconfigure`) before it is embedded.

## Flashing

```sh
BUILD="$PWD/build_rel" tools/flash.sh [PORT]
```

`BUILD` names the build directory. It defaults to `build` in the repository root. The
script reads three images from it:

- `bootloader/bootloader.bin`
- `partition_table/partition-table.bin`
- the first other `*.bin` in the build directory, which is the application

### Backup gate

Before it writes anything, the script requires `backup/original-flash-0x0-0x200000.bin`
and `backup/RESTORE.md` to exist. The image is not in the repository. To skip the check,
set `FORCE_NO_BACKUP=1`. Skip it only if you accept that the original firmware cannot be
restored from this host.

### Steps

1. Check the backup gate.
2. Find a download-mode serial port. If one is already present (`/dev/cu.usbmodem*`),
   skip to step 5.
3. Ask the running firmware to reboot into download mode:
   `POST /api/reboot?mode=download`.
   - A development build reboots at once. The script waits 20 s for the port.
   - A release build answers `202` with a confirm message. The script asks for BOOT to
     be held for 3 s within 30 s, and waits 40 s for the port.
4. If the HTTP request fails, try the FIDO HID route `tools/hidctl.py download`, then
   wait 20 s for the port.
5. If that fails too, wait up to 75 s for the development auto-recover reboot. A release
   build does not have this, so the script stops with an error. Hold BOOT, replug the
   board, and rerun.
6. Wait 1 s, then write the three images with `esptool`:
   `0x0` (bootloader), `0x8000` (partition table), `0x20000` (application). The script
   uses `--before no-reset` so the board stays in download mode. It does not write the
   NVS partition at `0x9000`.
7. Reset the board with `esptool` (`watchdog-reset`). If that fails, the script says to
   reset by hand.
8. Poll `http://192.168.7.1/api/status` once a second for 30 s. If it does not answer,
   the script stops and suggests `tools/bootlog.py`.

The waits and retries above are read from `tools/flash.sh`. They have not been timed on
a device for this repository.

### Settings and credentials across a reflash

A reflash by this script keeps the NVS partition. Settings, Wi-Fi credentials, and FIDO
credentials survive, as long as `partitions.csv` is unchanged. A full chip erase, or a
FIDO reset, removes FIDO credentials. This follows from the script and the partition
table. It was not re-tested on a device for this release.

### Restoring the original firmware

Follow `backup/RESTORE.md`. The image there uses the partition table of the original
factory firmware, which differs from `partitions.csv` in this repository.

## Host tests

These are standalone C programs. They are not part of the ESP-IDF build. Use a scratch
directory for the binaries (`$TMPDIR` below; set it or replace it with a directory you
choose):

```sh
cc -Wall -Werror -I main tools/lock_policy_test.c -o "$TMPDIR/lock_policy_test" && "$TMPDIR/lock_policy_test"
cc -Wall -Werror -I main tools/net_policy_test.c -o "$TMPDIR/net_policy_test" && "$TMPDIR/net_policy_test"
cc -Wall -Werror -I main tools/threats_test.c main/threats.c -o "$TMPDIR/threats_test" && "$TMPDIR/threats_test"
```

Exit code 0 means every check passed. These commands are written from the test headers.
They have not been run as part of preparing this repository.

`tools/threats_test.c` has comments that name `/tmp` paths. Those comments are not
commands the repository depends on.

## Dashboard

The dashboard is static files. Open `web/index.html?mock=1` in a browser to use the
simulated device in `web/js/mock.js`. Nothing is sent to hardware. Check the JavaScript
with:

```sh
node --check web/js/*.js
```

## Continuous integration

`.github/workflows/build.yml` runs the host tests, the dashboard syntax check, and the release
and development builds in the `espressif/idf:v6.0.1` container. Each build is merged into one
image (`s3-sentinel-release.bin`, `s3-sentinel-dev.bin`) with a SHA-256 file, and as three parts
(bootloader, partition table, application) for updates that keep NVS. A `v*` tag attaches them to a
GitHub Release. The test configuration is not built in CI. The workflow has not been
run yet. `.github/workflows/pages.yml` builds both images again on pushes to `main` and publishes
the parts with the browser flasher in `flasher/`.
